# 000 基盤とデプロイ

- 状態：実装中

## 背景・課題
名刺の QR コードと NFC タグは `https://tanijiri.dev/` を指す。名刺は「QR の飛び先が生きている状態」にしてから入稿するので、中身より先に「リポジトリに push すれば本番に出る」経路と、独自ドメインでの HTTPS 配信を用意しておく必要がある。
また、刷ったあとは URL を変えられないので、トップページが常に返ることを確認できる形にしておく。

## ゴール
- リポジトリの main ブランチに push すると、手作業なしで本番（`https://tanijiri.dev/`）に反映される。
- 独自ドメイン `tanijiri.dev` で HTTPS 配信される。
- 存在しないパスは 404 を返す（トップの内容を 200 で返さない）。
- デプロイとロールバックの手順が [docs/DEPLOY.md](../DEPLOY.md) に書かれている。
- 中身は仮のページ（名前とドメインだけ）でよい。本来の中身は spec 001・002 で作る。

## やらないこと
- サブドメイン（`blog.` `app.` など）の設定。将来の拡張として残す。
- 独自ドメインのメール受信設定（TASKS.md の名刺入稿前タスクで扱う。コードの変更を伴わないため仕様書にしない）。
- アクセス解析の導入（フェーズ2で検討）。
- CI での自動テスト（静的ページ1枚の段階では、下記のコマンドによる確認で足りる）。

## 設計方針
- 素の HTML＋CSS で、ビルド工程はない。公開するファイルは `public/` に置き、Pages の設定でビルドコマンドなし・出力ディレクトリ `public` にする。リポジトリは公開だが、`public/` の外（ドキュメント類）は配信しない。
- ホスティングは Cloudflare Pages（2026-09-29 決定）。デプロイは Pages の Git 連携（push をトリガーに自動デプロイ）を第一候補にする。リポジトリに API トークンを置かずに済むため。
- 404 用のページ（`404.html`）を用意する。Cloudflare Pages は 404 ページがないとトップの内容を返す動き（SPA 扱い）になるため、明示的に置く。
- `www.tanijiri.dev` もカスタムドメインとして追加し、Cloudflare のリダイレクト機能（Redirect Rules など）で `https://tanijiri.dev/` へ 301 で転送する。Pages の `_redirects` はパスのリダイレクト用で、ホスト名をまたぐ転送には使えない前提（実装時に確認する）。

## 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| Cloudflare Pages | 採用 | ドメインを Cloudflare で取得しており、同じダッシュボードでドメイン割り当てまで完結する。Git 連携での自動デプロイ、HTTPS も標準。 |
| GitHub Pages | 不採用 | 計画時に「こちらでも可」としていた。DNS を Cloudflare 側で別途設定する必要があり、管理画面が2か所に分かれる。 |
| Cloudflare Workers（静的アセット配信） | 不採用 | 静的サイトならどちらでも動く。ユーザーの判断で Pages にした。 |
| 静的サイトジェネレーター（Astro、Eleventy など） | 不採用 | 1ページ構成ではビルド工程と依存パッケージの管理が重荷になる。ページや記事の自動取得を足すときに再検討する。 |
| リンクまとめ系サービス | 不採用 | サービス終了で URL ごと消えるリスクがある。紙に刷る URL には使えない。 |

## 検証方法
- 自動テスト：なし（上記の理由）。
- スモークテスト／手動確認：AC1〜AC4・AC8 の `curl` コマンドを実行する（DEPLOY.md の「デプロイ後の動作確認」にも同じものを載せる）。AC5 は実際に push して確認する。
