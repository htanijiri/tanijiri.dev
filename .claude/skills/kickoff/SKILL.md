# キックオフ：BRIEF から初期ドキュメントを作る

チャットで相談してまとめた計画書 `brief/BRIEF.md` を読み、このプロジェクトのドキュメントを最初の状態まで作る。
**この作業では実装しない。** ゴールは、ユーザーが最初の仕様書をレビューして `合意済み` にできる状態にすること。

## 1. 事前確認
- `brief/BRIEF.md` がなければ、「計画書を brief/BRIEF.md に置いてから、もう一度 /kickoff してください」と伝えて終了する。
- `brief/` にほかの資料（画像、ワイヤーフレーム、チャットのログなど）があれば、それも読む。
- **すでにキックオフ済みか確認する。** `docs/specs/` に `001-` 以降の仕様書がある、または CLAUDE.md の冒頭の `<!-- -->` が埋まっている場合は、上書きせずにユーザーに確認する（「やり直す」「BRIEF の更新分だけ反映する」「やめる」のどれにするか）。

## 2. BRIEF を読んで整理する
BRIEF を最後まで読み、次の点を整理する。
- 何を作るか、誰がどの端末で使うか
- 解決したい課題と、あえてやらないこと
- 機能の一覧と優先順位（MVP に入れるものと、あとに回すもの）
- 制約（公開リポジトリにするか、データの扱い、予算、対象端末、期限など）
- 技術スタック（決まっているか、候補だけか、未定か）
- 決まっていないこと・曖昧なこと

**BRIEF にない前提は勝手に決めない。** 推測で埋めずに「実装前に人間が決める事項」に挙げる。おすすめがある場合は、理由と一緒に書き添える。

## 3. ファイルを作る・埋める
各ファイルの `<!-- -->` は、埋めたら消す。まだ埋められない部分（コマンド、デプロイなど）は `<!-- -->` を残しておく。

| ファイル | 書くこと |
|---|---|
| `CLAUDE.md` | 冒頭の一行の概要、「絶対に守ること」に追記するプロジェクト固有の制約、「技術スタック・設計方針」（決まっていれば。未定なら「未定：TASKS.md 参照」とだけ書く）。**テンプレートにもともとある共通ルール（仕様書の運用、ドキュメントの書き分け、作業ジャーナルなど）は消さない・書き換えない** |
| `README.md` | 概要、設計の前提、主な機能 |
| `TASKS.md` | 「実装前に人間が決める事項」、フェーズ分け（フェーズ1＝MVP）、各タスクに対応する仕様書の番号 |
| `docs/HISTORY.md` | 「このアプリは何か」「出発点となった要望」（BRIEF の要点）。BRIEF で決まっていた設計判断があれば「主要な設計判断」にも書く |
| `docs/TECH_NOTES.md` | 技術スタックが決まっていて、BRIEF に選んだ理由が書いてあれば「技術選定」に書く。なければ触らない |
| `docs/specs/NNN-機能名.md` | MVP の機能を1機能＝1ファイルで作る。`_template.md` をコピーして書き、状態は `ドラフト` にする。基盤づくり（開発環境、デプロイ先、検証の方法）が必要なら `000-` にする。未決事項は各仕様書の「未決事項」にも書く |
| `docs/specs/README.md` | 一覧表に、作った仕様書を追加する |

書くときの注意：
- `brief/` 以外のファイルは Git 管理され、公開される可能性がある。BRIEF に出てくる人名・社内の固有名詞・実際のパスやアカウント情報は、一般的な言い方に直して書く。
- 受け入れ条件は、コマンドや手順で確認できる形で書く（「いい感じに」「適切に」とは書かない）。
- `brief/BRIEF.md` 自体は書き換えない。

## 4. やらないこと
- 実装に着手すること（package.json などのコードやひな形を作ることも含む）
- 仕様書の状態を `合意済み` にすること（これはユーザーがやる）
- 技術スタックを勝手に決めること

## 5. 最後の報告
次の内容を短く伝える。
1. 作った・埋めたファイルの一覧
2. 「実装前に人間が決める事項」（決めてもらう必要があるものを、おすすめ案と一緒に）
3. 次にやること：仕様書（まず `000` または `001`）をレビューし、問題なければ状態を `合意済み` にしてもらう
